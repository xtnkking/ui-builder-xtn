# Personal UI v0.3.0 Hardening Roadmap

- Status: implementation in progress
- Baseline: `v0.2.19` at Git commit `0587d4b`
- Target: `v0.3.0`
- Last reviewed: 2026-09-27

For the complete remaining M4–M8 implementation breakdown, code entry points, acceptance evidence, focused-test rules, and model handoff prompt, read [M4–M8 execution and handoff plan](v0.3.0-m4-m8-execution-plan.md). This roadmap remains the scope and completion authority; the execution plan does not mark pending milestones complete.

## Purpose

This roadmap governs the next architecture-hardening cycle for `ui-builder-xtn`. The objective is not to add more component names. It is to make the existing enforced component platform internally consistent, behaviorally reliable, accessible, testable, documented, and reproducibly releasable.

A component fix is incomplete until its public contract, focused regression, representative example, and relevant documentation agree. The roadmap addresses both known defects and the mechanisms that must prevent those defects from returning.

## Scope Control

- Treat this document as the scope and completion authority for the `v0.3.0` hardening cycle.
- Before changing the Skill itself, identify the active milestone and its acceptance criteria. Do not silently work ahead into another milestone.
- Do not mark a milestone complete without recording its commit or artifact and verification evidence in the Progress Ledger.
- Do not add unrelated component families during this cycle. A new internal primitive is allowed only when it is necessary to solve a roadmap defect across existing components.
- Do not preserve a contradictory API only to avoid a breaking change. Record the migration and release it through `v0.3.0` instead.
- Do not change this roadmap's objective, remove an acceptance criterion, or expand its product scope without documenting the reason and obtaining user agreement first.
- During iteration, run the smallest focused checks that prove the current change. Run the complete release gate only at milestone boundaries and release review.
- Do not increment the public version, create a release, or push to GitHub merely because one milestone is complete. Publishing remains a separate explicit user decision.
- The user explicitly selected the MIT License on 2026-09-27. Preserve that choice in repository, package, and Skill metadata; do not silently substitute different distribution terms.

## Completion Outcome

At the end of this roadmap:

- public TypeScript types, runtime behavior, the Manifest, and both verifiers express the same rules;
- every existing visual export has a maintained example and every interactive export has meaningful behavioral and accessibility coverage;
- forms, overlays, advanced widgets, themes, and portals have explicit and tested contracts;
- a clean clone can validate, build, package, install, and reproduce a release without machine-specific dependencies;
- one Git repository is the only editable source of truth, while installed and backup copies are generated and verified artifacts;
- users can determine correct component usage from the explorer and generated API reference instead of guessing whether a failure belongs to the Skill or consumer code.

## Baseline Defects To Close

The cycle is not complete while any of these classes remains unresolved:

- protected component Props expose `className`, `style`, raw DOM `ref`, or other capabilities that the verifier later rejects;
- controlled and uncontrolled component modes allow contradictory or inert prop combinations;
- theme tokens accept arbitrary names, geometry can be overridden accidentally, or dark/system/inherit modes leave incorrect visual states;
- composite controls claim native `required` behavior through hidden inputs that do not participate in constraint validation;
- Lightbox or GuidedTour bypasses the shared modal stack, or Popover composition can produce nested interactive elements;
- CodeEditor creates a keyboard trap, or Tree, TreeSelect, Calendar, ContextMenu, and AsyncSelect lack their documented keyboard/ARIA model;
- component names promise capabilities beyond their implementation, including editor or virtualization behavior;
- browser tests depend on external environment variables, run only in Chromium, or are absent from CI and release gates;
- public API signatures can change without an API compatibility report and version-policy check;
- examples, API documentation, installer support, release tags, changelog history, licensing, or source synchronization remain manual or ambiguous.

## M0: Baseline And Source Authority

Deliverables:

- preserve `v0.2.19` as the immutable pre-hardening baseline;
- choose one Git worktree as the only editable source and make every other local copy a generated synchronization target;
- generate a stable public `.d.ts` or API report for all runtime exports;
- classify all 139 runtime exports as fixed visual control, layout, theme root, pattern, or non-visual API;
- create a machine-readable coverage matrix for API, owner, example, unit test, browser test, accessibility test, and stability status;
- record supported Node, React, TypeScript, package-manager, and browser ranges.

Acceptance:

- all 139 exports are classified and no unclassified export can pass validation;
- the API baseline and coverage matrix regenerate deterministically from a clean checkout;
- local Skill installation and backup directories are no longer treated as independent editable sources;
- the baseline can be restored without relying on a moving `main` branch.

## M1: Reproducible Quality Gate

Deliverables:

- adopt a repository-owned Playwright configuration and dependency;
- migrate the existing browser scripts into one standard runner;
- add component/unit tests and `@axe-core/playwright` accessibility checks;
- define Chromium, Firefox, and WebKit projects, with stable Chromium visual baselines;
- add `test:components`, `test:browser`, `test:a11y`, and `release:check` commands;
- add GitHub Actions for clean install, Manifest validation, strict enforcement, type/build checks, installer fixtures, browser behavior, and documentation build.

Acceptance:

- a clean clone runs all checks through documented package commands without `PERSONAL_UI_PLAYWRIGHT_MODULE` or another machine-specific module path;
- each known defect fixed after this milestone begins with a failing regression and ends with that regression passing;
- any required CI failure blocks release;
- focused development checks remain separate from the complete release gate.

## M2: Public API And State Contracts

Deliverables:

- introduce shared public Props utilities that omit protected styling escape hatches and internal ownership attributes;
- separate public Props from private slot/composition Props;
- replace raw DOM refs on fixed visual controls with a limited `controlRef` handle where focus, selection, or validity operations are necessary;
- provide an official form-library adapter rather than requiring consumer spread props;
- model controlled and uncontrolled value/open state as discriminated unions;
- add development-time errors for contradictory JavaScript prop combinations and controlled-mode switching;
- generate and commit an API compatibility report, with version-policy checks for every signature change.

Acceptance:

- a protected prop rejected by the verifier is also rejected by TypeScript;
- every call accepted by the public types is accepted by the verifier, and verifier-approved usage is type-correct;
- controlled mode requires its change callback, uncontrolled mode owns its state, and `value` cannot be combined with `defaultValue`;
- focus and form-library integrations work without exposing a mutable DOM styling handle;
- a public signature change without the appropriate version and API report fails CI.

Active inventory (2026-09-19, unreleased): the generated API report and registry currently identify 109 `fixed-control` exports. Of those, 99 expose `className`, 46 expose `style`, 10 expose a raw DOM `ref`, and 11 expose an internal `data-pui-owner` attribute. The verifier also has classification drift because its protected-component list is hard-coded instead of derived from `registry.json`. M2 therefore starts by locking the immutable `v0.2.19` API baseline and version policy, then introduces shared public Props/state/ref contracts, makes verifier protection registry-driven, migrates high-fanout primitives and forms, and finishes with the remaining controlled-state APIs plus a generated migration report. Public escape hatches must not be removed mechanically while private component composition still depends on them.

## M3: Theme And Portal Contract

Deliverables:

- replace the open-ended `--pui-*` record with a typed public semantic-token allowlist and matching runtime validation;
- keep control dimensions, radius, shadows, stacking, and other geometry internal unless a reviewed public variation is required;
- remove arbitrary `className` and `style` support from `ThemeProvider`;
- define complete `light`, `dark`, `system`, and true inherited theme behavior;
- move component-state colors, disabled states, skeletons, backdrops, scrollbars, and focus treatments to semantic tokens;
- make every portal surface inherit tokens and mode from its logical source theme;
- narrow or replace document-wide portal token observation and add a stress benchmark.

Acceptance:

- unknown tokens fail at type-check and runtime boundaries;
- theme definitions are the only approved location for raw theme color literals;
- light, dark, system, inherit, nested themes, and portal themes pass browser and screenshot regressions;
- core text and controls meet WCAG AA contrast requirements;
- large numbers of closed tooltips or overlays do not retain unnecessary global observers.

## M4: Forms And Overlay Kernel

Deliverables:

- replace hidden-input required bridges with one internal composite-control form contract;
- cover scalar and multi-value submission, `required`, `disabled`, reset, external `form`, error focus, and `FormData` behavior;
- extract one overlay/layer kernel for focus entry, focus trap, Escape, focus restoration, inert background, body scroll lock, nesting, dismissal policy, portal theme, and SSR safety;
- migrate Dialog, Drawer, ConfirmDialog, Lightbox, and GuidedTour to that kernel;
- make Lightbox keyboard-operable and either implement GuidedTour target positioning with stable fallback or remove the unsupported target contract;
- replace Popover's ambiguous `ReactNode` trigger with a canonical trigger API that cannot produce nested buttons.

Acceptance:

- an empty required composite control prevents submission and focuses its visible owner in all three browser engines;
- scalar/multi-value `FormData`, disabled behavior, reset, and validation state are correct;
- Tab cannot escape an active modal, Escape closes only the top layer, focus returns accurately, and scroll/inert state never leaks;
- backdrop, close control, and Escape policies remain independent after closing and reopening;
- rendered DOM contains no nested interactive triggers or duplicate accessible names.

## M5: Advanced Widgets And Capability Truth

Deliverables:

- implement a documented roving-focus and keyboard state machine for Tree and TreeSelect;
- implement correct grid ownership, date focus, month navigation, and announcements for Calendar;
- support pointer and keyboard opening, directional navigation, typeahead, and dismissal for ContextMenu;
- give AsyncSelect a complete combobox/listbox active-descendant contract and stable async-result reconciliation;
- make CodeEditor allow Tab to leave by default and provide an explicit, escapable indentation mode;
- audit Carousel, Accordion, virtualized data, editors, uploads, and other complex exports against their names and documented capabilities;
- implement missing production behavior or rename/deprecate overstated APIs with migration coverage.

Acceptance:

- each advanced widget is fully usable without a pointer and has only its intended Tab stops;
- disabled items and stale asynchronous options cannot become selected or active;
- automated keyboard assertions accompany axe checks; axe alone is not considered behavioral proof;
- no editor or virtualized component name promises behavior that the implementation and tests do not provide.

## M6: Component Explorer, API Docs, Locale, And Skill Routing

Deliverables:

- replace the five-tab demonstration shell with a searchable route per component family;
- register representative default, disabled/read-only, controlled/uncontrolled, loading, empty, error, validation, long-content, keyboard, mobile, overlay, and dark states where applicable;
- generate Props, defaults, state mode, keyboard model, ARIA, token, code example, and migration documentation from TypeScript plus Manifest metadata;
- turn the current component catalog into a generated index rather than a manually maintained API substitute;
- add a typed `LocaleProvider`, keep `zh-CN` as the default, and include `en-US` to prove that component and ARIA text is not hard-coded;
- keep business copy in consumer props and format dates, numbers, and plurals through `Intl`;
- shorten `SKILL.md` to durable source rules, routing, and completion requirements, with form/data/overlay/page details loaded from focused references.

Acceptance:

- all 137 visual exports have a compiled explorer case and all 5 non-visual exports have an API usage example;
- every interactive export has keyboard and axe ownership in the coverage matrix;
- adding a public export without an example and API page fails validation;
- locale keys are type-safe and complete, switching locale does not change component geometry unexpectedly, and public component source contains no unowned hard-coded UI or ARIA language;
- a user can find the supported API and behavior without reading implementation source.

## M7: Source Organization, Installer, And Release System

Deliverables:

- preserve the public barrel while moving implementation into clear foundation, input, navigation, data, feedback, overlay, pattern, and internal ownership boundaries;
- co-locate or explicitly bind component source, styles, tests, examples, and Manifest ownership;
- introduce CSS cascade layers for reset, tokens, base, components, and approved utilities;
- statically reject unlayered component CSS, duplicate protected selector ownership, excessive selector specificity, and unregistered tokens;
- support explicit package/project root and source root, npm/pnpm/Yarn workspaces, Vite, Next.js, monorepos, upgrade, deterministic dry-run output, and transactional rollback in the installer;
- create one release command for versioning, integrity refresh, validation, build, fixtures, packaging, checksums, installed-copy synchronization, tag preparation, and release notes;
- complete reliable historical changelog reconstruction, SemVer rules, migration notes, and the user-selected license.

Acceptance:

- the public barrel and supported usage remain stable through file reorganization unless a documented `v0.3.0` migration says otherwise;
- CSS no longer depends on accidental cross-file load order;
- supported project fixtures install, upgrade, verify, and roll back correctly;
- a clean clone reproduces release artifacts with one command;
- dry-run does not write, a failed release leaves no version or tag behind, and successful artifacts share the same version and hashes.

## M8: Independent Forward-Test And Release Review

Deliverables:

- install the release candidate into isolated projects and independently build a family login, CRUD list, complex form, searchable/paginated table, Drawer workflow, and nested modal flow;
- do not give the evaluating agent the expected implementation, suspected bug, or intended component mapping beyond the Skill and realistic user request;
- test migration of at least one realistic `v0.2.19` consumer;
- publish a local `v0.3.0-rc.1` artifact for final review before any public release;
- after explicit approval, create the immutable tag, GitHub Release, checksums, and verified installed copy.

Acceptance:

- independent consumers use registered public exports without native or third-party control reimplementation;
- all target projects pass typecheck, build, verifier, behavioral, accessibility, and responsive checks;
- the release matrix passes at 2560, 1440, 1024, 736, 360, and 320 CSS pixels where the component is responsive;
- the coverage matrix contains no missing owner, API, example, test, or documentation cell required for that export type;
- Git tag, GitHub Release, changelog, package, API report, checksum, canonical source, and installed copy identify the same immutable release.

## Global Definition Of Done

`v0.3.0` is complete only when all of the following are true:

- 142 runtime exports are classified and represented in the API report;
- 137 visual exports have maintained examples and the 5 non-visual exports have usage documentation;
- every interactive export has an explicit keyboard contract and automated accessibility ownership;
- no critical or serious axe issue remains in maintained examples;
- public TypeScript types and verifier policy agree;
- composite form controls, all modal surfaces, advanced widgets, theme modes, and portal inheritance pass their behavior suites;
- core behavior passes Chromium, Firefox, and WebKit, while responsive visual review passes all six required widths;
- clean-clone CI, installer fixtures, API compatibility checks, source integrity, Skill validation, and release reproduction pass;
- one Git source of truth, a complete changelog, a selected license, an immutable tag, a GitHub Release, and artifact checksums are present;
- the user has reviewed the release candidate and explicitly authorized public release.
